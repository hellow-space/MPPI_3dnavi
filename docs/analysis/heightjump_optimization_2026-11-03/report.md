# HeightJumpCritic 优化分析（尚未修改生产算法）

**结论：优先优化“连续坐标到九点栅格索引”的重复计算，并进一步复用相同邻域；不必先迁移 Eigen，也不建议先减少轨迹数量。** 当前实测的主要开销在查询坐标处理，而非读取高程 float 或计算九点极差。

后续实施：用户确认后已完成本报告第 1、3 项，结果见 [实施与验证报告](../heightjump_implementation_2026-11-03/report.md)。以下保留分析阶段记录。

本轮只新增分析程序、抽样数据和报告，没有修改 HeightJumpCritic、TerrainQuery、evaluate 或导航参数，没有启动导航或发送运动指令。

**已有基础与当前路径**

当前已采用 Release / `-O3 -fno-fast-math`、每轮持有不可变地图快照、缓存 elevation 矩阵指针、lambda 引用捕获、直接矩阵读取，以及轨迹第一次拒绝后停止检查后续预测点。以上不是待做优化。

尚在每个预测点重复执行：

```text
1000 条轨迹 × 56 个预测点
  → 轨迹位置变换至高程地图坐标
  → 每个位置采样 (x−r/x/x+r) × (y−r/y/y+r) 九点
  → 每个邻域点调用 isInside + getIndex + 存储边界检查
  → 读取 elevation，统计已知高度范围、unknown、outside
  → 返回二值可行性判断
```

全部通过时最多 504000 次邻域查询；本轮计数确认达到这个数。TF lookup、取快照和加锁在评分外层执行，不在每个邻域点内。当前最高优先级不在 TF / 锁，也不能再靠去掉层名查找获得上一轮同等收益。

**本轮本机组件测量**

7 × 7 m、0.1 m 栅格、固定随机种子 20261103，56000 个内部采样中心及其 504000 个邻域位置，平缓有限高程。预热 5 轮，统计 30 轮。调用现有 TerrainQuery / evaluate，与安装的库链接，未替换索引算法。

| 分别测量的工作 | P50 | P95 |
|---|---:|---:|
| 504000 次完整 TerrainQuery | 26.53 ms | 26.55 ms |
| 对同一批位置仅调用 isInside | 10.34 ms | 10.39 ms |
| 对已确认安全的同一批位置调用 getIndex + 存储边界检查 | 16.39 ms | 16.42 ms |
| 预先给好索引，仅读取相同矩阵数据及 finite 检查 | 0.56 ms | 0.67 ms |
| 56000 次完整九点评估 | 26.90 ms | 26.92 ms |
| 全 unknown、允许通行、保留起步区检查 | 27.52 ms | 27.53 ms |
| 同上，豁免回调改为无计算的 false，仅作为消融 | 26.49 ms | 26.52 ms |

**这些是分别测量的组件，不应相加，也不是可直接实现的“26.53 ms → 0.56 ms”加速承诺。** 预索引读取排除了生成索引本身，说明大部分优化空间在读取之前。全 unknown 消融比较得到相同的决策/unknown_count/高度差聚合值，但尚未对候选生产改法做完整回归。

此前完整 MPPI 离线消融中，保留 HeightJump 的优化器约 33.94 ms，关闭它约 4.39 ms，相差约 29.55 ms。这与本轮约 27 ms 的查询内核相符；差额不能直接当作本轮独立测出的其他函数耗时。

**重复邻域确实很多，但缓存键必须正确**

从故障包 `/trajectories` 在约 +1、8、12、20、26、31 秒各抽取一帧候选显示点，结合录包中该时刻之前最近的高程地图几何，使用真实 GridMap 的索引接口统计：

| 帧 | 候选显示点 | 不同中心格 | 不同九点索引组合 |
|---|---:|---:|---:|
| +1 s | 3800 | 92 | 92 |
| +8 s | 3800 | 123 | 123 |
| +12 s | 3800 | 113 | 113 |
| +20 s | 3800 | 40 | 40 |
| +26 s | 3800 | 34 | 34 |
| +31 s | 3800 | 27 | 27 |

合计 22800 个显示点、429 个“按帧分别统计的不同邻域”，显示出很强的复用空间。它们是原配置下抽稀发布的轨迹点，不是完整 1000 × 56 状态；录包最近地图也不保证就是控制器内部当时使用的那份快照，不能把这里的命中比例当成完整评分缓存命中率。

尤其不能直接假设“同一个中心格永远是同样九格”：

- 0.1 m 分辨率、0.1 m 半径的边界探测中，69 个被测中心格有 15 格出现多个九点索引组合，单格最多 4 种。
- 0.13 m 分辨率、0.1 m 半径时，53 格中有 52 格出现多个组合，单格最多 3 种。

原因包括连续采样位置、半径与分辨率关系、浮点取整和地图边界。这是实际调用现有 GridMap 接口得到的结果。邻域索引不同，就可能读到不同障碍高度；不能未经验证地直接以栅格中心统计替代连续位置采样。

**建议的优化顺序**

1. **专用的九点索引路径：第一优先级。**

   评分前缓存地图中心、长度、分辨率、尺寸、循环缓冲起始索引；针对已经验证水平的 GridMap 几何，将坐标处理集中在一次邻域查询中。九点只有 3 个 x 和 3 个 y，分别计算后组合读取九个高度，避免每个点重复两轴换算。与当前 9 次各含两轴处理相比，轴坐标转换数量有机会从 18 次降到 6 次，具体实现仍以测量为准。

   必须保持实际算术和取整规则，保留有限值检查、地图范围和最终存储索引保护。不能简单删掉 isInside；现有回归已经覆盖过极大有限坐标引发浮点到整数异常的情形。先保留当前 TerrainQuery / evaluate 作为参考，差分验证专用路径。

   此项不要求改 MPPI 公共 API，也不依赖 xtensor / Eigen 替换，是比较集中的优化。

2. **邻域统计复用：收益潜力最大，正确性工作也更多。**

   针对同一不可变地图快照，复用已经查到的九点基础统计，例如 min/max、已知数、unknown 位图和 outside 标志。可以评估按需缓存实际九点索引组合，或对可证明采样格不变的内部区域使用逐格预计算，边界和特殊几何回退原路径。

   仅把完整查询结果放入哈希表不一定快：为了得到缓存键仍计算九次 getIndex，可能保留了主要开销。因此应结合第一步的轴索引复用，测量键构造、查表和统计总成本；不能只展示很高命中率。

   7 × 7 m / 0.1 m 地图只有 4900 格，适合评估每份新快照建立基础统计表。地图约 10 Hz 更新、控制约 20 Hz，但这只是摊销条件，不是收益证明：预计算耗时、未查询区域的浪费和缓存构造造成的 P95 / P99 抖动都要算入。

   缓存必须与快照身份、地图几何/滚动索引、半径及相关配置绑定。新输入无效、地图过期和时钟异常仍必须按原规则失败。更新时建立新快照后再发布，避免一轮评分混用新旧缓存。

   **不要无条件缓存最终 Pass/Reject。** unknown 禁止通行时，起步区豁免依赖实际采样点坐标；即使读到相同的九个格子，豁免仍可能不同。优先缓存基础统计，保留坐标相关的策略判断。当前 unknown 允许通行的配置可以使用更简单的快路径，但通用实现还必须支持原有 false 策略。

3. **允许 unknown 时跳过不起作用的起步区计算：低风险小收益。**

   当前 `unknown_is_traversable=true` 时，最终决策不使用 `all_unknown_exempt`，但每次遇到 unknown 仍可能执行坐标反变换和 hypot。可以在这一条件下跳过这部分，仍统计 unknown、outside、高度差并保留优先级。当前 synthetic 全 unknown 测量节省约 1.03 ms；真实收益取决于 unknown 比例，不应作为主要加速来源。

4. **为评分提供仅返回决策的快速路径：次优先级。**

   HeightJumpCritic 只用 `evaluate(...).decision`。一旦已知高差达到阈值，最终必为 HeightJump，可以不再读取余下邻域点。但现有 evaluate 还返回完整 observed_jump / unknown_count；直接提前返回会改变它的结果契约。因此应保留参考完整接口，独立评估 decision-only 路径。平地全部通过时几乎没有收益，台阶或坏区域可能收益更大。

   不宜先遇到 outside / unknown 就返回：后续已知点可能形成优先级更高的 HeightJump 判定。最终二值代价可能一样，但分类与诊断会变，不能宣称判定完全一致。

5. **线程并行、GPU、减少轨迹点：后续再考虑。**

   按轨迹并行在结构上可行，但 Jetson 的其他线程还要运行定位、高程建图和 DDS，需要评估整机 P95 / P99、调度和额外 CPU 占用；不适合在明显的重复查询仍存在时优先增加线程。GPU 涉及数据共享、传输与同步，对这张小地图不应先做复杂迁移。

   减少 batch_size、time_steps、增大栅格或隔点跳查都会改变控制或地形检查，不能算本轮保持判定的优化。也不应启用 `-ffast-math`，因为 NaN / Inf 在当前协议中有明确的 unknown 语义。

**建议验收**

先做第 1 项，并顺带评估第 3 项；测量后再决定是否值得做第 2 项。将 HeightJump 约 30 ms 降到 10 ms 以内可作为阶段目标，**这是目标，不是当前已经达到的实测值**。

对照必须包含：

- 原始与优化路径在 decision、unknown_count、observed_jump 上一致；decision-only 接口单独比较 decision。
- 平地、斜坡、台阶、窄高障碍；阈值上下与恰好等于；NaN、Inf、部分/全 unknown。
- 0.05 / 0.10 / 0.13 m、半径 0.10 / 0.17 m；非正方形地图、循环索引、地图边缘和内部栅格边界及相邻浮点数。
- unknown 两种策略、起步区边缘、坐标系变换；地图替换时旧快照仍在使用、无效输入与过期恢复。
- 性能记录包含每张新地图的缓存构建、每轮评分、完整 MPPI 和真实输入/录包负载；不能仅报热缓存最好值。
